# ReGIS：同一段输入结束后的第一次强制重绘

之前的 XTerm 参考在**每一步**后重绘，可能改变后续步骤的历史。此次[托管 Linux 捕获](https://github.com/xiongnemo/nemoterm/actions/runs/44470058582)用固定源码 `5c75ead9a75d4b2e666ca06fa94503b5766ed93f` 构建 XTerm。每个步骤终点都从新的 XTerm 进程开始，先送同一段输入，再只在最后一次截图后强制重绘。10 个终点（含三组对照）分别整段和逐字节运行，共 20 个进程。每个进程的初始画面、每步输入、状态应答和重绘前的完整窗口 RGB 都与原始历史记录一致；没有强制清理、传输差异或对照失败。

下表比较 `810a26f` 的 MSVC 终端组件实际生成的 160×120 图像。数字是不同的像素数。每格整段和逐字节结果相同。

| 原参考场景（步骤从 0 起） | 组件与首次显示 | 组件与同一窗口第一次强制重绘 |
|---|---:|---:|
| 向上滚屏 2 | 101 | 0 |
| 向下滚屏 1、2 | 各 303 | 各 0 |
| 换行滚屏 2 | 202 | 0 |
| 共享 ReGIS 调色板改色 1 | 600 | 0 |
| 擦行 1、2 | 各 0 | 各 101 |

这次排除了「前一步强制重绘影响后一步」对这七个差异的解释。擦行原始画面中被擦掉的 101 个像素，在 XTerm 首次强制重绘后重新出现；Nemoterm 的擦行结果保留。其他五处在 XTerm 首次强制重绘时变成与组件相同的图。不能据此把组件当成 Windows 的首次呈现，也不能把原始 CI 标成成功。

[原始截图及观测](regis-first-expose-captures.zip)按原样保留所选 XTerm 截图、应答日志和 MSVC 实际差异图；`source.json` 列出每个文件的 SHA-256、两个原始制品的 ID 和摘要。[逐帧结果](regis-first-expose-810a26f.json)列出受测组件标识及每个差异区域的边界。下列命令仅分析已有文件，不运行终端：
