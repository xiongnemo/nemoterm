# 应用只要求拉高或拉宽窗口时

`CSI 9;2 t` 让窗口纵向最大化，`CSI 9;3 t` 则横向最大化。普通最大化是 `CSI 9;1 t`，恢复为 `CSI 9;0 t`。这些操作保留标题栏；`CSI 10;1 t` 是另一个操作，它进入无边框全屏。这里用 `CSI` 表示 ESC 加 `[`，数字之间没有空格。

**旧版实际表现。** `f2f553b9` 把非零参数都当作普通最大化。Windows 标签窗口原来的左右边界是 `(26, 725)`，要求只拉高时，实际左右边界却变成了 `(-8, 1032)`；这时 Windows 已将它标为最大化。独立窗口也一样。应用在「禁止远程调整窗口大小」或「锁定窗口大小」配置下仍可最大化窗口。两个窗口内 36 个几何和权限检查只通过 12 个。[旧版原始制品](https://github.com/xiongnemo/nemoterm/actions/runs/44680175234/artifacts/14603833745)。

**原版对照。** 在 [XTerm 412 和 Openbox 3.6.1 的托管 Linux 桌面](https://github.com/xiongnemo/nemoterm/actions/runs/44680844954/artifacts/14604376248)上，新进程外框初始为 `(93, 71, 547, 324)`，以下四个数按左、上、右、下排列。表中每个场景均使用新进程，确认窗口管理器已经接管窗口，每个指令都收到了终端状态回复。

| 指令 | 应用后的外框 | 再单独发送 `9;0` |
| --- | --- | --- |
| `9;2` 纵向 | `(93, 0, 547, 768)` | 精确回到初始外框 |
| `9;3` 横向 | `(0, 71, 1024, 324)` | 精确回到初始外框 |

连续请求另记：先 `9;2` 再 `9;3`，原版确实从纵向切到了横向；最后 `9;0` 的实际外框是 `(93, 0, 547, 757)`，与这次进程初始外框不同。另两个组合分别覆盖从普通最大化切为单轴，以及单轴切为普通最大化。Windows 采用共享顶层窗口的原始位置作为恢复位置；不会因为一个中间状态覆盖用户原来的窗口大小。此行为和原版独立列出。

**修复版 `6a8986d5`。** [同一份单 EXE 的实际 Windows 回放](https://github.com/xiongnemo/nemoterm/actions/runs/44681200960/artifacts/14604009011)从 **12/36 提高到 36/36**：普通、禁止远程调整大小和锁定窗口三种配置，在独立窗口和标签窗口都核对全部四条边、边框与最大化状态。另有 **11/11** 个双标签场景：后台标签不能改动窗口或退出前台全屏；换到另一标签可以恢复原窗口大小；用户自行调整后的尺寸不会被过期的恢复请求覆盖。完成后两个子程序和前端均正常退出。上述 ZIP 的 `candidate/original.zip` 是本次 GitHub 原始制品。
