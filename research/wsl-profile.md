# WSL Bash 配置方案：新标签、重新打开和退出

开发候选 `c621b171` 在「配置方案 → Shell」增加「x64 WSL 会话使用 Linux PTY」。默认关闭。点击「保存并应用」会保存到当前配置方案；已经打开的 Bash 继续使用原终端。同一窗口 `Ctrl+Shift+T` 打开的新标签和下次启动时，新会话读取保存值。本页测试的是 GitHub 托管 Windows 上的 WSL1，不是用户机器，也未验证 WSL2。

[候选构建](https://github.com/xiongnemo/nemoterm/actions/runs/44625439750/artifacts/14579531431) 是 4,921,344 字节的单个 EXE，SHA-256 `7e27f1dbf1430322aaa9763a54ea7c517f38efef4a563cfc4b21bc5753aed288`。PE 资源 40003 内嵌的 x86-64 Linux 程序 SHA-256 为 `8e292a12251c09a74349a17ab78b148ff7f819d2fa1dd19c48eb43279875a8fb`。`fc769def` 试用版仍需用环境变量选择此功能。

[实际设置窗口和独立对照](https://github.com/xiongnemo/nemoterm/actions/runs/44627561380)：不设传输环境变量，按通常方式从配置启动 Bash，没有用自定义命令替换它。

| 操作 | 远程观测 |
| --- | --- |
| 默认启动，在设置里勾选并保存 | 保存值从缺省变为 `1`。原 Bash PID 9，父进程 `/init`，终端 `/dev/tty1`；保存前后相同。 |
| 实按 Ctrl+Shift+T，然后关闭新标签 | 新 Bash PID 110，终端 `/dev/pts/0`，父进程的 ELF 散列与 PE 内嵌资源相符。关闭后只剩原标签、PID 9 和 `/dev/tty1`，临时 ELF 已删除。 |
| 关闭再打开相同配置；取消勾选并保存 | 先读到 `1`，新 Bash 确实在 `/dev/pts/0`，父进程为匹配的 ELF。保存值变为 `0`，当前 Bash 无变化；再次打开恢复 `/dev/tty1`，无 ELF。 |
| 配置值为 `1` 时指定 Windows PowerShell | 运行中的 PowerShell 回报 `Desktop`；没有 ELF，所有被跟踪的进程在退出后 4 秒内消失。 |

**退出检查仍失败。** 三次 WSL 配置启动中，前端均返回 `0`，也未留下临时 ELF；但每个 Windows 作业在前端退出 4 秒后仍有两个名为 `init` 的进程。它们在这条期限之后约 11 秒自行退出。完全不启动 Nemoterm、直接运行 `wsl.exe` 的两个对照（登录 Bash 和单独的 `/bin/true`）均留下同名、同数量的进程，约在相同时间自行退出。由此可见，此现象不需要 Nemoterm 或其 ELF 就会出现；未更改 4 秒门槛，也没有强杀进程。该项仍记失败，不计为整套通过。

同一 EXE 的其他结果：中英文实际设置窗口在 100%、125%、150%、175%、200% 下共完成 44 次 Shell 页检查，新标签文字完整、未遮住底部按钮。Vim 和 tmux 在两种渲染器、两种 TERM 下 8/8 通过。粘贴原始字节的 12/12 组匹配；4/4 组按行读取的拼接内容正确，但读到了五段，Linux 对照目标为两段。真实全屏客户端选区 10/10 通过。24 轮普通对话的前端私有工作集峰值为 pterm 3,768,320、GDI 5,763,072、DirectX 10,022,912 字节；这些数字不代表满屏压力峰值。

[原始回执与可复核记录](wsl-profile-c621b171.zip)保留三个阶段的配置测试（含原始失败）、独立 WSL 对照、应用与粘贴记录、内存样本和二进制身份；DPI 取自原始制品中的 44 份设置记录，完整制品 ID、散列与所选文件名见包内 `artifacts.json`。

[同一候选的完整交互回执](wsl-profile-interaction-c621b171.zip)为 **79/81**。两项未过的是 Codex 启动早期的窗口按键组和实际键盘组：窗口按键两种绑定、实际键盘 Ctrl+V 都在等待附件时超时。等正式输入框就绪后，两种途径 × 两种绑定都收到正确图片，OpenCode 的两组也通过。六种 160×48 满屏负载在 GDI、DirectX 各通过六项；前端私有工作集峰值是 **19,714,048 / 29,499,392 字节**，总工作集峰值为 54,493,184 / 74,866,688 字节。这是 `c621b171` 的结果，不代替后续改动版本的验收。

## 内嵌 WSL PTY 的像素尺寸（`bda4d485`，修复前）

[托管 Windows / WSL1 实测](https://github.com/xiongnemo/nemoterm/actions/runs/44707689192/artifacts/14615219402)使用同一份试用 EXE（SHA-256 `ac45d753b7072265bb2d41bc4f29cd30549f3e384d012838113cc51172726744`）。同一个 Linux 子程序分别查询终端的字符格、行列数和 Linux `TIOCGWINSZ`；测试还独立读取 Windows 客户区尺寸。GDI、DirectX 结果相同，子程序均正常退出。

| 阶段 | 字符网格 | 实际文字区（像素） | Linux PTY 回报（像素） |
| --- | --- | --- | --- |
| 启动 | 80×24 | 640×480 | 0×0 |
| 拉大窗口 | 84×27 | 672×540 | 0×0 |
| 放大字号 | 74×25 | 666×525 | 0×0 |

三次的 VT 查询均与窗口测量一致，Linux PTY 的行列数也正确。另建一个不经过 NemoTerm 的 PTY，直接写入 80×24 / 640×480，能原样读回；保持 80×24 仅把像素改为 720×504，读回的仍是 640×480；改为 87×31 / 696×620 后则读回新值。因此需要区分两个问题：当前内嵌转发器只传行列，而这台托管 WSL1 即使直接设置尺寸，也未保留仅变更像素的更新。该次运行保留原始失败，不代表 WSL2 的行为。

## 修复后：程序能读到哪些像素尺寸？（`032bb830`）

同一份 [GitHub 构建的 Windows x64 单文件](https://github.com/xiongnemo/nemoterm/actions/runs/44709431096/artifacts/14616159271)，SHA-256 `78d80809569f5f12a8b3651e5af4b3c7b83ceaf02ad7d9acf0026b3843422a64`。REA 静态检查确认是原生 PE；资源 40003 里的 38,304 字节与由[托管 Ubuntu 从源码编译](https://github.com/xiongnemo/nemoterm/actions/runs/44708799179/artifacts/14616735465)的 ELF 完全相同。两次构建之间保留了旧 ELF 尚未更新时的校验失败；在候选提交重编后，要求逐字节相同的检查已通过。

| 内嵌 WSL1 会话中的操作 | 实际文字区 | Linux 子程序 `TIOCGWINSZ` | 终端查询 |
| --- | ---: | ---: | ---: |
| 打开 80×24 窗口 | 640×480 | 640×480 | 640×480 |
| 拉大到 84×27 | 672×540 | 672×540 | 672×540 |
| 外框不变，放大字号，变为 74×25 | 666×525 | 666×525 | 666×525 |
| 另开 80×24 窗口，锁定行列，改变字体尺寸 | 800×576 | 640×480（旧值） | 800×576 |
| 仍保持 80×24，再增大一格的宽和高 | 880×600 | 640×480（旧值） | 880×600 |

GDI 和 DirectX 的读数逐项相同，四个窗口均正常退出。最后一步，Linux 程序先收到了主动通知 `CSI 48;24;80;600;880 t`，然后才发 `CSI 14 t` 查询并收到 `CSI 4;600;880 t`，两者均与实际窗口相符。只用 `ioctl` 的应用不会自动得到这项补偿。独立 PTY 对照在托管 WSL1 从主端或从端设置都读到旧像素；相同 ELF 在原生 Ubuntu 上五组读数全对，包括不改行列和大于 32,767 的像素值。没有改动内核，也没有为刷新像素而临时向应用报告虚假的行列数。未测试 WSL2。

真实 WSL 图片的显示也单独核对过：`img2sixel` 输出经独立解码后，与 GDI、DirectX 的窗口裁图比较，绘制前、绘制后、重绘后、擦除后共八个阶段像素差均为零。[原始前后对照、内核与窗口回执，以及逐项结果](wsl-pty-pixels-032bb830.zip)包含固定行列时仍失败的检查。[同 EXE 的主动通知专项](https://github.com/xiongnemo/nemoterm/actions/runs/44710846215)。
