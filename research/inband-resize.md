# 调整窗口和字号后，程序实际收到了什么？

程序可以随时用 `CSI 18 t` 查询行列数。启用[尺寸变化通知（模式 2048）](https://gist.github.com/rockorager/e695fb2924d36b2bcf1fff4a3704bd83/a1e61ea1782326e975b6e4cfe0c538bac54c1f42)后，它还应当立即收到一次尺寸，随后由终端主动报告变化。`CSI 48;行;列;高;宽 t` 的像素数只计算完整文字单元，不含标签栏、边框或放不下一格的余量。这是现代终端扩展；没有把 XTerm 412 当作这个模式的参考实现。

| 真实窗口的操作 | 旧试用版 `bdf847f9` | 候选 `04cecf23` 的子程序实际读到 |
| --- | --- | --- |
| 订阅，当前为 80×24 | 查询返回未知模式 | 24 行、80 列，文字区 640×480 像素；再次订阅也立即报告 |
| 放大窗口到 84×27 | 能主动查出新尺寸，未收到通知 | 27 行、84 列，672×540 像素 |
| 外框不变，放大一档字号 | 能查出新单元尺寸，未收到通知 | 25 行、74 列，666×525 像素；对应单元 9×21 像素 |
| 取消订阅，或执行硬复位后再改尺寸 | 无通知 | 无通知，接下来的实际键盘输入仍能收到 |

每版都在 GitHub 托管 Windows 桌面上运行独立 GDI 窗口、GDI 标签页、独立 DirectX 窗口、DirectX 标签页，字体为 SarasaTermSC Nerd Light。扩大后的终端客户区为 678×546 像素，与文字区的差正好是四周各 3 像素的边框。Win32 客户区、子程序读到的行列数以及原始输入字节分别记录。四个旧窗口均通过 6/15 项，新窗口均通过 15/15 项；八个进程均正常退出。[旧版回放](https://github.com/xiongnemo/nemoterm/actions/runs/44701550282) · [首版修复](https://github.com/xiongnemo/nemoterm/actions/runs/44702412206)。

首版修复的 Linux 核心测试另有一次失败：测试只尝试处理 64 个回调，未读到两次预期通知。将测试改为在真实队列末尾放入标记后，处理到标记共执行了 1,358 个回调，预期字节全部收到，ASan/UBSan 通过。没有更改产品等待策略，也没有替换最初的失败日志。[修订后独立运行](https://github.com/xiongnemo/nemoterm/actions/runs/44703215110)。

候选 `bda4d485`（EXE SHA-256 `ac45d753b7072265bb2d41bc4f29cd30549f3e384d012838113cc51172726744`）额外记录每一次 `ReadFile` 返回的字节以及紧接着的 Win32 `GetConsoleScreenBufferInfo`。四个新窗口均通过 **19/19 项，共 76/76**。在收到 `CSI 48;27;84;540;672t` 的那一次读取后，Windows 查询已经返回 84×27；字号放大后，收到 `CSI 48;25;74;525;666t` 时也已经是 74×25。取消订阅和硬复位后，各窗口都只读到用于结束观察的按键 `9`。这验证了所测操作的实际接收时序；没有测量连续拖动时的全部中间位置。
